| 位置                      | 一句话职责         | 判定它是否越界的判据                  |
| ----------------------- | ------------- | --------------------------- |
| `main.py`               | 装配：把零件接成 app  | 出现 `@app.get` 或处理业务数据的 `if` |
| `config.py`             | 外部输入的唯一边界     | 代码里出现字面量（IP、key、URL）        |
| `.env` / `.env.example` | 让配置能进库、密钥不能进库 | `.env` 出现在 `git ls-files` 里 |
| `api/health.py`         | 两个端点，两种故障动作   | 两个端点查的是同一批东西                |
| `core/errors.py`        | 全服务的错误形状      | 任何模块自己拼错误 dict              |
| `tests/`                | 在应用外面锁住契约     | 测试文件出现在 `app/` 里面           |

## 1. `app/main.py` —— 装配层

**是什么。** 全项目唯一的装配点，46 行，只做四件事：`FastAPI(...)` 建空壳、`include_router` 挂路由、`add_exception_handler` 注册错误处理、`lifespan` 定义启停钩子。核心是 `create_app()` 这个工厂函数，调一次产出一个互不干扰的 app 实例。

**为什么这么设计。** 因为"用什么零件"和"零件怎么造"必须能分别变化。装配线工人不生产螺丝，他只按图纸把别人造好的螺丝拧到孔位上 —— 螺丝挪个位置，改装配这一行；螺丝本身要换型号，改上游模块。两件事不互相牵连，才有后面的一切：测试能造干净实例、换实现不动业务、故障时一屏看懂服务形状。

**不这么做会怎样。** 具体后果不是"代码丑"，是**测试从 0.42 秒的纯内存跑，变成必须连数据库**。因为 `tests/` 里写的是 `with TestClient(app) as client:`，`with` 会触发 lifespan，而 lifespan 定义在 `main.py`。`main.py` 里塞了什么，测试就跟着跑什么。本地 `.env` 指向本地库所以是绿的，CI 容器里没有库 → 3 条测试全部 error → 你 push 完看到"我什么都没改，CI 红了"。

**一行判据。** 打开 `main.py`，看到 `@app.get` 装饰器、或者一个 `if` 在处理业务数据，就已经不是装配台了。

**诚实备注。** `main.py` 顶部的 `structlog.configure(...)` 严格说也属于"配置"而非"装配"，理想位置是 `core/logging.py`，由 main 调用一次。W1 阶段留着可以接受，但你要能说出它为什么不太对 —— 这是审自己代码的能力。

## 2. `app/config.py` —— 环境边界

**是什么。** 所有外部输入的唯一边界。一个 `Settings(BaseSettings)` 类，前缀 `FDE_`，从 `.env` 读（`env_file=".env"`），`extra="ignore"` 让无关环境变量不报错。六个字段：`app_name`、`env`、`log_level`、`llm_base_url`、`llm_api_key`、`llm_model`。最后一行 `settings = Settings()` 是模块级单例。

**为什么这么设计。** 因为 dev 和 prod 对同一份代码的要求是**相反**的：dev 要"多说"（DEBUG 日志、完整堆栈、能随便改），prod 要"闭嘴"（INFO、对外只说"服务内部错误"、不能泄表名和路径）。同一份代码要同时满足两个相反要求，差异就只能从外面注入，不能写死在代码里。这就是十二要素应用的第三条：**配置存在环境中**。

**不这么做会怎样。** 三个具体场景：

1. 代码里写死 `env="prod"`，本地调试时日志一片 INFO，你查不出问题，只好临时改成 dev 再改回来 —— 改回来那次忘了提交，生产就开始打 DEBUG。
2. 生产环境抛异常时把堆栈直接返回给客户端，堆栈里有表名、文件路径、SQL 片段。客户截图发到群里之前，这些已经出去了。
3. key 写在 `config.py` 的默认值里，跟着代码进了 git、进了镜像、进了每一个开发者的电脑。

**判据。** 在 `app/` 目录里 grep 一遍 `http://`、`sk-`、数字端口 —— 有命中就是越界。

**取舍说明。** `settings = Settings()` 是模块级单例，意味着"import 那一刻环境就被固化了"。测试想跑两套配置就得重造 `Settings(...)` 或 reload 模块。W1 接受这个取舍（简单、够用）；等真需要多配置测试时，再改成依赖注入 —— 现在改是过度设计。

## 3. `.env` 与 `.env.example` —— 让配置能进库，让密钥不能

**是什么。** 一套两文件机制。`.env.example` **进库**，只写键名、值留空或写安全默认值；`.env` **不进库**，由开发者复制一份填真值。`.gitignore` 里有 `.env` 这一行。

**为什么这么设计。** 因为 git 保存的是**全量历史**。你 commit 一次密钥，下一个 commit 删掉也没用 —— `git log -p` 永远翻得出来，`git checkout` 到那个 commit 也拿得到。所以"事后清理"这条路不存在，唯一可行的策略是**从未进入**。`.env.example` 的作用是让新人（和三个月后的你）知道"这个项目需要哪几个配置项"，同时一个真值都不给。

**不这么做会怎样。** 密钥 = 身份 + 付费凭证。你的仓库是公开的，公开仓库有专门的爬虫在扫，量级是**分钟级**不是天级。泄露后的正确处理不是"改掉那个 commit"，是**立刻到服务商吊销并重建 key** —— 因为从它被公开的那一刻起就不可信了，你也不知道对方刷了多少。账单是你的。

**三个落地动作**（自己跑，别看我说）：

```bash
git check-ignore -v .env                  # 有输出 = 确实被忽略
git log --all -S "sk-" --oneline          # 空 = 历史里从没出现过
git ls-files | grep -x ".env"             # 空 = 没被跟踪
```

**一个容易漏的点。** `.env` 是**本地开发**的加载方式，生产环境不应该存在 `.env` 文件 —— 配置由编排层（docker compose 的 `environment`、k8s 的 Secret、云厂商的参数存储）注入成真正的环境变量。如果生产也靠 `.env`，说明注入链路根本没打通，只是把密钥从代码里挪到了服务器文件里，泄露面没变小。

## 4. `app/api/health.py` —— 两个端点，两种故障动作

**是什么。** 两个端点。`/healthz`（liveness）只返回 `{"status":"ok"}`，永不查依赖；`/readyz`（readiness）检查依赖清单，任一失败返回 `503`，并带 `checks` 明细。

**为什么这么设计。** 判据是**失败后系统会做什么动作**，不是"它检查什么"：

|        | `/healthz`                | `/readyz`               |
| ------ | ------------------------- | ----------------------- |
| 语义     | 这个进程还能响应 HTTP 吗           | 我现在能接流量吗                |
| 消费者    | 容器存活探针（k8s livenessProbe） | 负载均衡（Service endpoints） |
| 失败后的动作 | **杀掉容器重启**                | **把我从流量池摘掉**            |
| 查依赖吗   | 绝不                        | 必须查                     |
| 失败返回码  | 非 200 即可                  | 503                     |

两个动作完全不同 —— 一个杀进程，一个不给流量 —— 所以必须是两个端点。合并以后，系统就失去了"只摘流量不杀进程"这个选项。

为什么 liveness 绝不能查依赖：数据库挂了，重启我的进程一万次数据库也不会回来。重启是唯一无效且昂贵的动作。

为什么 readyz 返 503 而不是 500：503 的语义是"暂时不可用，稍后重试"，会引导上游等一会儿再来；500 是"我这有 bug"，会触发告警电话。选错码，监控就失真。

**不这么做会怎样。** 只有一个 `/health` 且它查数据库时：数据库主从切换（典型 20–60 秒），探针连续失败 → T+15s 判定死亡 → 杀容器 → 冷启动 90 秒 → 还没暖完又被判死 → 所有副本连锁 CrashLoop。**一个 30 秒的抖动被放大成 10 分钟不可用**，而且恢复后还要人工介入。

**现状备注。** `checks = {"config": True}` 是 W1 的占位，W2 要接真实依赖（LLM 凭据、向量库、磁盘）。注意 `readyz` 返回的是 dict 而不是 bool —— 目的就是挂了以后能一眼看出是哪个依赖挂了，而不是只有一个"不健康"。

## 5. `app/core/errors.py` —— 错误契约

**是什么。** 全服务的错误形状，四样东西：`AppError` 基类、两个子类（`BadRequestError` 400 / `UpstreamError` 502）、统一的 `_payload()`、两个 handler（业务异常 / 兜底未捕获异常）。

**三字段 + 第四个字段的分工。**

```python
{"error": {"code": "invalid_param", "message": "参数不对", "request_id": null}}
```

| 字段            | 位置       | 谁消费                  | 作用                                    |
| ------------- | -------- | -------------------- | ------------------------------------- |
| `status_code` | HTTP 状态行 | 负载均衡、CDN、监控、客户端 SDK  | 决定链路上每一跳的行为：4xx 不重试、503 稍后重试、5xx 触发告警 |
| `code`        | body     | 你的代码、前端 `if` 分支、告警规则 | 区分"同一个 400 底下的五种不同原因"                 |
| `message`     | body     | 人（调用方开发者、最终用户）       | 可以直接展示的一句话，不能是 `KeyError('page')`     |
| `request_id`  | body     | 你（排障时）               | 串起一次请求的全部日志行，用户报这个串你就能定位              |

**为什么要三个而不是一个。** `status_code` 是红绿灯，只有 5 档，只能说"错得多严重"；`code` 是显微镜，能说"错在哪一件"。只有红绿灯，前端没法区分"参数缺失"和"参数超范围"，只能统一弹一句"请求有误"；只有显微镜，负载均衡看不懂，不知道要不要重试。

**类属性 + 实例覆盖的规则。** `AppError` 把 `code` 和 `status_code` 定义成类属性给一档默认值，子类按类别改，实例参数按具体情况改：

```python
BadRequestError("参数不对", code="invalid_param")   # 类别仍是 400，但精确到"哪个参数"
```

规则一句话：**`status_code` 按档定，`code` 按件定。** 由此能立刻识别出一个坏配对：`status_code=500` 配 `code="not_found"` —— 客户端传错 id，却触发了 5xx 告警电话。这种误报三次之后，人就学会不看告警了，那套监控等于废了。

**不这么做会怎样。** 每个模块自己拼错误 dict：有人返回 `{"msg": ...}`、有人返回 `{"detail": ...}`、有人直接 `raise HTTPException`。前端要为 N 种形状写 N 套解析；监控无法按 `code` 聚合，只能数 500 的总数；用户报错只截图，你既没有 `code` 也没有 `request_id`，只能靠猜。

## 6. `tests/` —— 在应用外面锁住契约

**是什么。** 三条测试，`test_health.py` 两条（healthz 形状、readyz 的 checks），`test_errors.py` 一条（错误形状）。总共 0.42 秒，零外部依赖。

**为什么放在 `app/` 外面。** 三个理由，每个都是硬理由：

1. **测试是开发期产物，不该进镜像**。放 `app/tests/` 里，打包时会被一起带走，生产镜像里躺着一堆用不上的测试代码和断言消息。
2. **依赖方向会被搅乱**。`tests/` 引用 `app/` 是正常的单向依赖；一旦把测试塞进 `app/` 里面，"测试引用业务"和"业务引用测试"就混在一起，那条"箭头只许朝下"的线就废了。
3. **测试不该参与运行时**。它不注册路由、不进 lifespan、不影响任何请求。

**"锁住契约"锁的是什么。** 看这一行：

```python
assert set(body["error"]) == {"code", "message", "request_id"}
```

它断言的是**键的集合**，不是值。多一个字段红、少一个字段也红。所以它不测逻辑，它测形状 —— 这就是契约测试。以后谁"顺手"把 `request_id` 改名成 `trace_id`，CI 立刻红，而不是等前端解析崩了、客户在群里发截图。这就是 `test_errors.py` 文件头那句注释的意思："这条测试的价值在于锁住契约"。

**不这么做会怎样。** 错误结构被改了没人拦，上线后前端 `body.error.code` 变成 `undefined`，所有错误提示退化成"未知错误"，而你在后端日志里一切正常。

**现状备注（诚实版）。** `test_errors.py` 里用 `@app.get("/__test/bad")` 往全局 app 上注册了一个测试专用路由 —— 这个路由会真的留在 app 实例上，属于轻微污染。更干净的做法是 `app = create_app()` 造一个独立实例再往上注册。这恰好又是 `create_app()` 存在的理由：**能造新实例，才有干净的测试**。
